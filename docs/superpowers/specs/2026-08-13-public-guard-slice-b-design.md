# 設計書：公開ガード（スライスB）＋手書き台本ライブラリ

- 日付: 2026-08-13
- ステータス: 設計承認待ち
- ブランチ: `feature/public-guard`
- 関連: [同居デプロイ設計（スライスA）](2026-08-09-deploy-same-origin-design.md) §1「非スコープ」で本スライスに送られた項目

## 1. 背景とスコープ

スライスA（同居デプロイ）が完了し、本番URL <https://kojirase-daigekijo-production.up.railway.app> が稼働している。実機での録音・採点・共有も確認済み。

しかし**現状の本番は、URLを知っていれば誰でも何度でもゲームを回せる**。1ゲームごとに Anthropic（台本生成1回＋採点1回）と Groq（人数分の文字起こし）へ課金が発生し、コード側にこれを止める仕組みが一切ない。**URLを広く配れないのはこれが理由**であり、本スライスはその歯止めを入れる。

### コストの実測値（設計の前提）

- 台本生成・採点とも `claude-haiku-4-5`（input $1.00 / output $5.00 per MTok）
- 文字起こしは Groq `whisper-large-v3-turbo`（Anthropic 比で微小）
- ざっくり **1ゲーム 4〜5円**。日20ゲームで月約3,000円、日100ゲームで月約15,000円

### 決定事項（ブレインストーミングで確定）

- **上限は極端に低く始める**（既定 `DAILY_GAME_LIMIT=5`）。実際の使われ方を見てから環境変数で上げる。
- **上限到達時はエラーにせず、手書き台本＋スタブ採点で遊べる状態を保つ**（スライスAからの継続方針）。
- **上限が低い以上、上限到達は例外ではなく日常**になる。現行の `scriptStub.ts` は「（スタブのセリフ）」と画面に出す開発用の仮物なので、そのままでは「遊べるまま」が成立しない。よって**スライスCの最小版（手書き台本ライブラリ）を本スライスに前倒しする**。
- **台本は `plays/` ディレクトリに JSON ファイルとして置く**。台本ごとに対応人数レンジを宣言する方式（ディレクトリをジャンル×人数で切る案、必須役＋任意役で1本が全人数を賄う案は却下。理由は §5）。

### 非スコープ

- 台本の中身の充実（構造と読み込みだけ作り、本数は後から足す）
- カウンタの永続化（理由は §3）
- WebSocket ハンドシェイクのオリジン検査
- 認証・アカウント・課金

## 2. ゲートをどこに置くか

課金が発生するのは2箇所しかない。

| 地点 | 呼び出し | 課金 |
|---|---|---|
| [handlers.ts:245](../../../server/src/handlers.ts) `start_game` | `generateScript` | Anthropic 1回 |
| [handlers.ts:78](../../../server/src/handlers.ts) `finalizeEvaluation` | `evaluatePerformance` | Groq × 人数 ＋ Anthropic 1回 |

どちらも **Socket.io イベントであって HTTP ではない**。したがって Express のレート制限ミドルウェアでは課金の本体を守れない。ここが本スライスの設計上の要点である。

### 採用：`start_game` の入口で1回だけ判定し、そのゲームのモードを固定する

```
start_game（台本生成の直前）
  ├─ 枠あり → 枠を1消費 → room.aiMode = true  → 実AI台本 → 実AI採点
  └─ 枠なし → 消費しない → room.aiMode = false → 手書き台本 → スタブ採点
```

`Room` に `aiMode: boolean` を持たせ、`finalizeEvaluation` はそれを参照する。

- **消費単位は「1ゲーム＝1回」**。同じルームで結果画面からロビーへ戻り再度開始すれば、また1回消費する（2回目も台本生成が走るため）。
- **中断しても枠は返さない**。台本生成の課金はすでに発生しているため。返すと中断連打で無限に回せる穴にもなる。

### 却下：AI呼び出し地点ごとに個別判定

台本生成の直後に枠が尽きると「AI台本なのにスタブ採点」というちぐはぐな体験になる。枠の消費タイミングが2箇所に分かれて状態も複雑になる。ゲーム単位で一貫させるほうが説明しやすく、判定も1箇所で済む。

## 3. 日次上限カウンタ

新規 `server/src/quota.ts`。

```ts
tryConsumeGame(now: Date): boolean          // 枠があれば消費して true
getQuotaState(): { date, used, limit }      // 表示・ログ用
__resetQuotaForTest(): void
```

- 「今日」は **JST の日付文字列**で判定する。日付が変わったら `used` を 0 に戻す。
- 状態は `{ date: string, used: number }` の1組だけ。ルーム単位・IP単位ではなく**サーバー全体で1本**の枠。

### カウンタはメモリ上のみに持つ

Railway のコンテナはファイルシステムが揮発するため、ファイルに書いても再デプロイで消える。外部ストア（Redis 等）は別サービスのコストと運用が増え、この規模では見合わない。

**したがって再デプロイ・クラッシュ再起動でカウンタはリセットされる。** これは受け入れる。再起動は頻繁ではなく、かつ**最後の砦は Anthropic / Groq コンソール側の支払上限**である（これが未設定なら、アプリ側に何を入れても本当の歯止めは存在しない）。

## 4. キルスイッチとレート制限

### 環境変数

| 変数 | 既定 | 効果 |
|---|---|---|
| `DAILY_GAME_LIMIT` | `5` | 1日にAIを使えるゲーム数 |
| `AI_ENABLED` | `true` | `false` で枠に関係なく全ゲームを手書き台本＋スタブ採点に |
| `PUBLIC_ENABLED` | `true` | `false` で新規ルーム作成を拒否（進行中のゲームは継続させる） |

いずれも Railway の変数画面から変更 → 再デプロイで即座に効く。値の解釈は新規 `server/src/config.ts` の1箇所に閉じ込め、**不正値・未設定は既定にフォールバックする**（`DAILY_GAME_LIMIT=abc` でサーバーが落ちないこと）。

### レート制限は自前で1モジュール

新規 `server/src/rateLimit.ts`。`express-rate-limit` は**入れない**。Socket.io 側はどのみち自前実装になるため、HTTP と Socket.io で別々の仕組みを持つより、同じ小さなモジュールを両方から使うほうが単純で、テストも書きやすい。

| 適用先 | 閾値（同一IP） | 目的 |
|---|---|---|
| `create_room`（Socket.io） | 60秒に 5回 | 荒らし・ルーム乱造の抑制 |
| `POST /upload`（HTTP） | 60秒に 30回 | multer が検証前に最大25MBをRAM展開するため、メモリ枯渇の抑制 |

`/upload` の 30回は「最大10人 × 複数ゲーム」を想定した緩めの値。ここは正常なプレイを止めないことを優先し、絞るのは日次上限の役目とする。

`start_game` には**レート制限を掛けない**。日次上限がすでに課金を止めており、二重に掛けると正常なプレイの邪魔になるだけだからである。

閾値は定数で持つ（環境変数を増やさない）。上限に達したときは接続を切らず、`error` イベント／HTTP 429 を返して**そのリクエストだけ**を落とす。

### ⚠️ `trust proxy` が必須

Railway はプロキシ経由で到達するため、`app.set('trust proxy', 1)` を設定しないと `req.ip` が全員同一になり、**レート制限が全ユーザーをまとめて1人として扱う**。

さらに **`trust proxy` は Express の設定であり Socket.io には効かない**。Socket.io 側は `socket.handshake.headers['x-forwarded-for']` を取る必要があるため、新規 `server/src/clientIp.ts` に両方の取り出しを集約する。

> **実装時の訂正**: 当初は「先頭を取る」としていたが誤りだった。`x-forwarded-for` は各プロキシがホップごとに「自分から見た直前の相手」のアドレスを**末尾に追記**していく方式のため、クライアントがヘッダを自分で送って偽装すると、その偽装値が先頭に来てしまう。信頼できるプロキシが1段だけの構成では、**末尾**の値こそがそのプロキシ自身が観測したアドレス＝偽装できない値である。よって実装（`clientIp.ts`）は末尾を採る方式で確定した。

## 5. 手書き台本ライブラリ

### 置き場所と読み込み

- リポジトリ直下 **`plays/`** に1ファイル1台本の JSON を置く。
- パス解決は既存の `.env` 読み込み（[index.ts:10](../../../server/src/index.ts)）と同じく**モジュール位置基準**にする。cwd 基準にすると起動ディレクトリの違いで取りこぼす。
- **起動時に全ファイルを読んで検証し、メモリに保持する。** 不正なファイルは警告ログを出して**スキップし、サーバーは起動を続ける**（1本の不備で全体を落とさない）。
- 台本を足したら再デプロイで反映。ホットリロードはしない。

### ファイル形式

`ScriptData`（`worldSetting` / `roles` / `entries`）に変換できる形にする。**セリフは役の下にぶら下がらず独立した並びで、その順序が劇の進行そのもの**である点に注意。プレイヤー名は実行時に決まるため、台本ファイルは**役を添字で参照する**。

```jsonc
{
  "id": "romance-cafe",
  "genre": "romance",            // GENRE_IDS のいずれか
  "title": "閉店15分前",
  "minPlayers": 2,
  "maxPlayers": 5,
  "worldSetting": "閉店間際のカフェ。雨が降っている。",
  "roles": [
    { "role": "店長",   "description": "..." },   // 1人目に割り当て
    { "role": "常連客", "description": "..." },   // 2人目
    { "role": "バイト", "description": "..." }    // 以降 maxPlayers 人目まで
  ],
  "entries": [
    { "roleIndex": 0, "action": "ため息をつく", "line": "……もう閉めるか。" },
    { "roleIndex": 1, "line": "待って、まだいるんだけど。" }
  ]
}
```

### 人数への対応

参加人数 N のとき：

1. `roles` の**先頭から N 件**を使い、参加順にプレイヤー名を割り当てる
2. `entries` のうち **`roleIndex < N` のものだけ**を残す（順序は保つ）
3. `ScriptEntry` に展開する（`player` = 割り当てたプレイヤー名、`character` = その役名）

したがって台本作者の制約は「**先頭 `minPlayers` 役だけでも劇として成立し、`maxPlayers` 役まで足せる**」ように書くこと。`maxPlayers` を欲張らないほうが書きやすい。

### 台本の選択

```
1. genre 一致 かつ minPlayers <= N <= maxPlayers  → その中からランダム
2. なければ genre 不問 で人数が合うもの          → その中からランダム
3. それもなければ 現行の generateStubScript       → 開発用フォールバック
```

②があるため、**台本が1本もない組み合わせでも穴が空かない**。これがディレクトリをジャンル×人数で切る案を却下した理由でもある（8ジャンル × 3レンジ = 24枠を埋めきらないと穴が残り、結局①②相当の代替ロジックが必要になる）。

「必須役＋任意役で1本が全人数を賄う」案も却下した。台本の本数は最小で済むが、任意役のセリフを「欠けても劇が成立する」ように書く必要があり、執筆が最も難しく、劇として薄くなりやすい。

### 採点

手書き台本モードのゲームは既存の `generateStubScores`（名前から決定的にスコアを生成）をそのまま使う。スコアと講評と称号が出るため、画面は成立する。

## 6. プレイヤーへの表示

`RoomSnapshot` に `aiMode: boolean` を追加し、簡易モードのときだけロビーに控えめな一文を出す（「本日のAI枠は終了しました。簡易モードで遊べます」）。

黙ってスタブに落とすと「AIの採点がおかしい」と受け取られる。このゲームは「AIが台本を書き、AIが採点する」ことが売りなので、そうでない回はそう伝えるほうが誠実である。

### ⚠️ 既知の罠（このスライスで踏みうるもの）

- **`RoomSnapshot` に `aiMode` を足すと全リテラルに波及する。** server は `tsx` が型チェックしないため、`npx tsc --noEmit` が実質のゲートになる。テストダブルの修正漏れはこれでしか見つからない。
- 統合テストで `io.to` の同時配信を待つときは、**両方のリスナを登録してから emit** する（逐次 await はホスト側を取りこぼす。Windows で再現性100%）。

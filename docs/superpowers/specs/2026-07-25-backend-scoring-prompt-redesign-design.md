## 1. 背景とスコープ

Phase C3 で採点（Whisper 文字起こし→Claude Haiku 4.5 評価）が実キーで動くようになったが、**プロンプトは「まず動く」最小構成のまま**で、ゲームの盛り上がりの核心が model の初期値任せになっている。具体的な弱点:

- 3軸（演技力／感情表現／こじらせ度）を **1〜5 で採点させているが、各軸の定義も 1〜5 のアンカーも無い**。
- 講評コメントの**語り口・長さが未指定**で、当たり障りのないコメントになりがち。
- 即興での台本逸脱を加点とするか減点とするかが未定義。

本スライスは**採点プロンプトの設計し直し**＋**称号（アワード）フィールドの新設**に絞る。台本生成プロンプトの改善は別スライス（非スコープ）。

### 決定事項（ブレインストーミングで確定）

- **講評の語り口＝辛口お笑いホスト**（イジりに愛・必ず1つ本気で褒める・人格/容姿/声質そのものへの攻撃と差別/下ネタは禁止・イジる対象は演技の中身のみ）。
- **こじらせ度＝恥を捨てた振り切り度**（オーバーさ・本気度・恥のかなぐり捨て具合）。
- **出力の形を拡張**：プレイヤーごとに **`title`（称号）** を1つ追加する。称号はアワード風（「感情爆発賞」「本日の大根役者」「MVP」）でも**キャラ描写風（「激情型アクター」「悲劇の主人公タイプ」「闇落ち演技職人」）でもよい**＝その人の演技の特徴を捉えたもの。全員で重複させない。
- **モデルは `claude-haiku-4-5` のまま**（1ゲーム1回の呼び出し・コスト最小。まずプロンプトで質を上げ、不十分なら後日モデルを上げる — [[public-launch-cost]]）。
- **採点ルーブリックの作り込み方＝案A**（濃いルーブリック＋ペルソナを SYSTEM に指示文で。few-shot 例は入れない。実キーで甘い/辛いと感じたら後日 few-shot を後付け）。

### 既知の罠（Phase C3 で確定・本スライスでも順守）

- **Anthropic 構造化出力（`output_config.format`）の JSON Schema は `minimum`/`maximum` に加え `maxLength`/`minLength` も非対応**。→ 追加する `title` は `{ type: 'string' }` のみとし、**長さ（12文字目安）はプロンプトと parseScores で担保**。整数3軸も従来どおり min/max を付けず parse でクランプ。
- **Claude は指定名を verbatim で返さない/人数分返さないことがある** → `parseScores` の fail-open（名前一致→順番→プレースホルダ／1〜5クランプ）を維持する。

## 2. アーキテクチャ方針

- **プロンプトの静的部分（ペルソナ・ルーブリック・アンカー・称号指示・ガードレール・出力規約）は `SYSTEM` に集約**、**per-game の可変データ（worldSetting・各プレイヤーの役/台本の台詞/実際の発話）は `buildScorePrompt` に**、という現状の分離を踏襲する。
- **`title` は必須フィールド**として `PlayerScore` に追加する。任意にしないことで、`tsc`（client build）とサーバーテストが**全ての PlayerScore 構築箇所（実採点・スタブ・parseScores のプレースホルダ・クライアントのモック等）を型エラーとして炙り出す**＝実装漏れの安全網。
- 既存の頑健化（fail-open parse・generationトークン・非同期 finalize）は一切壊さない。

## 3. データ契約（`shared/types.ts`）

`PlayerScore` に `title` を追加:

```ts
export interface PlayerScore {
  playerName: string
  acting: number
  emotion: number
  kojirase: number
  comment: string
  title: string   // 称号（追加）
}
```

## 4. サーバー実装（`server/src/ai/scoreGen.ts`）

### 4.1 SCORE_SCHEMA

`items.properties` に `title: { type: 'string' }` を追加し、`required` に `'title'` を追加。**`title` に `maxLength` は付けない**（構造化出力非対応）。整数3軸は従来どおり min/max なし。

### 4.2 SYSTEM プロンプト（全面刷新）

以下の要素を含む（文面は実装時に確定・下記は確定した内容）:

- **ペルソナ**: バラエティ番組の辛口お笑いホストの審査員。台本の役/台詞と実際の発話（文字起こし）を照合し、テンポよくイジりながら採点。
- **ガードレール**: イジりに愛を。各プレイヤーに必ず1つは本気で褒める点を入れる。イジる対象は「演技の中身」のみ（声質・容姿・人格そのものへの攻撃、差別的・下ネタ表現は禁止）。
- **3軸を各1〜5の整数で採点**（1〜5全域を使い、全員3〜4の団子を避ける）:
  - 演技力: 声の張り・キャラの一貫性・台詞の説得力。1=棒読み/聞き取れない、3=普通に演じている、5=引き込まれる名演。
  - 感情表現: 喜怒哀楽の起伏・抑揚・感情の乗り。1=無感情で平板、3=そこそこ感情が乗る、5=感情が爆発して伝わる。
  - こじらせ度（＝恥を捨てた振り切り度）: オーバーさ・本気度・恥のかなぐり捨て具合。1=淡々と棒立ち、3=そこそこノっている、5=完全に振り切って恥を捨てている。
- **逸脱の扱い**: アドリブ・台本からの逸脱は、役や世界観に沿って振り切っているほど加点材料（特にこじらせ度）。ただし支離滅裂・世界観を壊すものは評価しない。
- **空発話**: 聞き取れなかった扱いで各項目を最低点(1)にし、辛口ホスト調でその旨をコメントに書く。
- **comment**: 2〜3文の日本語。可能な限り実際の発話や場面に具体的に触れる（例「あの『諦めないで』の絶叫だけは本物」）。
- **title（称号）**: その人の演技の特徴を捉えた短い称号（12文字程度まで）。アワード風でもキャラ描写風でもよい。全員で重複させない。
- **既存の頑健化指示を維持**: playerName は与えられた名前を一字一句そのまま使い、全プレイヤーをちょうど1件ずつ含める。出力は必ず与えられた JSON スキーマに厳密に従う。

### 4.3 buildScorePrompt

現状維持（worldSetting＋各プレイヤーの 役/台本の台詞/実際の発話を提示）。per-player ブロックの提示順が `parseScores` の順番フォールバックの前提である点も不変。変更は無し、または軽微。

### 4.4 parseScores（fail-open 維持＋称号）

- `RawScore` に `title?: unknown` を追加。
- 正常エントリ: `title: String(s.title ?? '')` を追加。
- プレースホルダ（該当エントリ無し）: `title: '—'`（UI が崩れない中立表記。空文字でも可だが `—` を採用）。
- fail-open の骨子（名前一致→未使用エントリを順番→プレースホルダ／`clampScore` で1〜5）と「真に壊れた出力（不正JSON・scores 非配列）のみ throw」は不変。

### 4.5 スタブ（`server/src/ai/scoreStub.ts`）

`generateStubScores` の各要素に `title` を追加（例 `title: '演技派（スタブ）'` など決定的な文字列）。型を満たすため必須。

## 5. クライアント実装

### 5.1 ResultScreen（`client/src/screens/ResultScreen.tsx`）

各プレイヤーの表示に称号を追加（名前の近くにバッジ/サブテキスト）。既存レイアウトを踏襲し最小追加。

### 5.2 scoreCard（`client/src/scoreCard.ts`）

ルームカードの各プレイヤー行・個人カードに称号を描画。**カードは Phase D で「内容・見た目は暫定・後日ユーザーが仕様変更予定」の合意があるため、称号の追加は最小限**に留める（描画は scoreCard.ts 内に隔離）。

### 5.3 その他の PlayerScore 構築箇所

`title` を必須にするため、クライアント/共有で `PlayerScore` を**リテラル構築している箇所（モック・フォールバック等）**はすべて `title` を追加する必要がある。`npm run build`（tsc）で全て炙り出される。

## 6. テスト戦略

- **サーバー（`server/src/ai/scoreGen.test.ts` 拡張）**:
  1. `SCORE_SCHEMA` が `title` を含み、かつ `maxLength`/`minLength`/`minimum`/`maximum` を含まない（構造化出力非対応の制約回帰）。
  2. `parseScores` が正常 JSON から `title` を抽出する。
  3. `parseScores` のプレースホルダ経路でも `title` が埋まる（人数不足時）。
  4. 既存の fail-open ケース（名前不一致→順番、名前一致優先、範囲外クランプ、不正JSON throw）を維持。
- **クライアント**: テストフレームワーク無し＝`npm run build`（tsc && vite build）clean ＋ 実機/2タブ目視（称号・辛口講評が出る／団子採点でない／称号がカードに載る）。
- **実キー確認**: Haiku 4.5 で辛口ホスト調＋称号が生成されるか、各軸が1〜5全域に散るかを2タブで目視。

## 7. 非スコープ / 繰り越し

- **台本生成プロンプトの改善**（ジャンル別作風・人数対応・few-shot 等）は別スライス。
- few-shot 例の同梱（案B）は本スライスでは入れない。実キーで採点が甘い/辛い/称号が弱いと感じたら後日追加。
- モデルのアップグレード（Sonnet 5 等）は本スライスでは行わない（Haiku 4.5 維持）。
- カードの内容・見た目の本改修は Phase D の合意どおり後日（本スライスは称号の最小追加のみ）。

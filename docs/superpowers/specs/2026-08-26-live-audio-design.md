# リアルタイム演技配信（ライブ音声）設計書

- 日付: 2026-08-26
- 対象: サブプロジェクト **D**（4分解の最後から2つ目。C は本設計の副産物として同時に手に入る）
- 前提: main HEAD `d4b300b`（ローカル複数プレイヤー A+B マージ済み）

---

## 1. 目的

**離れた場所にいるプレイヤーが、互いの演技を聞きながら掛け合えるようにする。**

現状、オンライン参加のプレイヤーは相手の声が一切聞こえない。台本を見てタイミングを推測しながら、実質「虚空に向かって演じる」状態になっている。これを直すのがこの機能である。

同じ部屋にいる人同士は生の声が既に聞こえているので、この機能の主対象ではない（むしろハウリングの原因になる）。

## 2. 決定事項サマリ

| 論点 | 決定 |
|---|---|
| 想定する場面 | **離れた場所の人同士**。同室者向けではない |
| 接続の確実性 | **ベストエフォート**。無料の STUN のみ。TURN は導入しない |
| 繋ぐフェーズ | **録音中だけ音が出る**。接続自体は準備フェーズで張る |
| ON/OFF の主体 | **ホストが部屋全体で決める**（ロビー。ジャンル選択と同じ場所・同じ作法） |
| トポロジ | **mesh（端末どうし）**。ホスト経由のスター型は採らない |
| 音の配線 | リモート音声は **`<audio>` 要素で再生**し、録音用に **mixDest へ分岐** |
| マイクの取得 | **1本だけ**。`addTransceiver` で先に接続を張り、録音開始で `replaceTrack` |
| 失敗時の再試行 | **しない** |
| 追加コスト | **1ゲームあたりゼロ**（AI を呼ばず、STUN は無料） |

## 3. なぜこの形か

### 3.1 ベストエフォートを選ぶ理由

WebRTC の P2P は、モバイルキャリアの CGNAT 下で一定割合が失敗する。これを救う TURN 中継サーバーは従量課金であり、このプロジェクトは AI 課金を月$5に絞っている性格と合わない。

**接続に失敗しても、ゲームの中核（録音・アップロード・採点・結果）は完全に無傷である。** 失敗した相手の声が聞こえないだけで済む。この性質があるからこそベストエフォートが成立する。

### 3.2 mesh を選ぶ理由

ホスト経由のスター型は接続数を減らせるが、**ホストが落ちると全員の音が消える**という依存が増える。このコードベースは既に「ホスト切断＝即解散」という弱点を抱えており、そこに荷重を足したくない。

**接続はプレイヤー単位ではなく端末単位で足りる。** これはローカル複数プレイヤー（A+B）の成果で、`deviceId` が既に接続の同一性そのものになっている。1台に3人乗っていれば、その端末は3人ぶんの声が入った1本を送るだけでよい。

mesh は端末数の2乗で増えるため上限を設ける（6.1節）。

## 4. サーバー側：中継に徹する

**サーバーは SDP も ICE も理解しない。** 宛先を検証して右から左へ流すだけである。WebRTC の知識をサーバーに持ち込むと、ブラウザの実装が変わるたびにサーバーを直すことになる。

### 4.1 部屋の状態

```ts
// server/src/roomStore.ts の Room に1つ追加
liveAudio: boolean   // ホストがロビーで決める。既定 false
```

`resetRoom` では**保持する**（ジャンルと同じ扱い。同じ部屋で再戦するとき毎回付け直させない）。

`RoomSnapshot` にも `liveAudio: boolean` を追加する（後から参加した人・再接続した人が現在の設定を知るため）。

### 4.2 イベント

| イベント | 向き | payload |
|---|---|---|
| `set_live_audio` | C→S | `{ enabled: boolean }` |
| `live_audio_changed` | S→C | `{ enabled: boolean }` |
| `rtc_signal` | C→S | `{ toDeviceId: string; data: unknown }` |
| `rtc_signal` | S→C | `{ fromDeviceId: string; data: unknown }` |

`set_live_audio` のガードは `set_genre` と同じ：**ホストのみ・`status === 'waiting'` のみ**。

**シグナリングを1イベントに束ねる理由**: offer / answer / candidate で3つに割ると、サーバーが「いまどの段階か」を知っている風の構造になる。実際には知る必要がなく、知らないほうが壊れない。`data` は `unknown` のまま素通しする。

### 4.3 `rtc_signal` の検証

`toDeviceId` はクライアントが自由に指定できる。`deviceId` は全員に配られているため、**同じ部屋の他人になりすまして接続を仕掛ける**ことが原理的に可能である。次を全部通す：

1. 送信者が部屋にいる（`deviceBySocket`）
2. **宛先が同じ部屋にいる**（別の部屋の端末は指定できない）
3. `room.liveAudio === true`
4. `room.status` が **`casting` または `recording`**
5. 宛先が切断中でない（`disconnectedAt == null`）

**条件4で `'preparing'` を含めない理由（重要）**: `RoomStatus` には `'preparing'` が宣言されているが、**サーバーはこの値を一度も代入していない**（`room.status = ` の代入箇所は `waiting` / `casting` / `recording` / `evaluating` の4つだけ）。準備フェーズはクライアント側の画面遷移にすぎず、そのあいだサーバーの状態は `'casting'` のままである。つまり**接続を張る準備フェーズは `'casting'` に含まれる**。

`'preparing'` が使われていないこと自体は既存の小さな綻びだが、`RoomStatus` から消すと波及が広いので**この設計では触らない**。ただし「`'preparing'` を条件に入れれば準備フェーズが通る」と誤読すると、**シグナリングが一切中継されず機能全体が動かない**ので、実装時に必ずこの節を読むこと。

さらに **`fromDeviceId` はサーバーが解決して付ける**。クライアントの自己申告は使わない。これで「別人を騙って offer を送る」経路が閉じる。

### 4.4 レート制限

ICE 候補は1接続あたり数十件がバースト的に飛ぶ。このコードベースはルーム作成・アップロード・感想にそれぞれレート制限を持つので、同じ流儀で粗い網を1つ張る：**1端末あたり、1ゲーム中に中継できるシグナル数の上限**。

```ts
// server/src/roomStore.ts の Device に1つ追加
signalCount: number   // resetRoom で 0 に戻す

// server/src/limits.ts の Limits に1つ追加
rtcSignalMaxPerGame: number   // 既定 500
```

**500 の根拠**: 上限6台＝1端末あたり5ピア。1接続で offer/answer 各1＋ICE候補が多くて30程度なので、5ピアで概ね160件。異常時のバーストを見込んでその3倍を取る。正常なプレイを止めないことを優先し、絞るのは荒らし対策としての粗い網に徹する。

超えたら**黙って捨ててログに残す**（`console.log`。既存のレート制限と同じ流儀）。エラーイベントは返さない——シグナリングは大量に飛ぶので、返すと今度はエラーが溢れる。

カウンタは `Device` に持たせ、**`resetRoom` で 0 に戻す**。`waiting` は必ず `resetRoom`（または部屋の新規作成）を経て到達するので、これで1ゲームごとにリセットされる。

### 4.5 端末数の上限

```ts
// shared/constants.ts
export const MAX_LIVE_AUDIO_DEVICES = 6   // mesh は端末数の2乗で増える（6台＝15接続）
```

- ロビーで端末数が上限を超えていたらトグルを無効化し、理由を表示する
- **`start_game` の時点で `liveAudio && devices.size > MAX_LIVE_AUDIO_DEVICES` なら、サーバー側で `liveAudio` を false に落として `live_audio_changed` を流す**

サーバー側の落とし込みが必要なのは、ロビーで ON にしたあとに人が増えた場合があるため。クライアントの表示だけに頼らない。

## 5. クライアント側

### 5.1 マイクは1本だけ取る

**接続を準備フェーズで張りたいが、マイクは録音開始まで動かしたくない。**

前提として押さえておくこと: **このアプリは既に録音中に `getUserMedia` を2本並行で呼んでいる**。`recorder.ts`（採点用＋鑑賞用）と `RecordingScreen.tsx` の音量メーターがそれぞれ独立に取得しており、本番で動いている。つまり「同時に複数取ると必ず壊れる」わけではない。

その上で、ライブ音声のために**3本目を取ることはしない**。理由は3つある:

1. 並行キャプチャは iOS Safari で後発が先発を中断させる事例が報告されており、**本数を増やすほどリスクが上がる**。録音はこのアプリの成果物なので、そこに賭けない
2. 準備フェーズから自前でマイクを取ると、**録音していない時間帯にマイクが動く**ことになる
3. 3本目を取らずとも、下記の方法で**必要な性質がすべて得られる**（早期の ICE 完了・録音開始と同時の発声・`recorder.ts` 無変更）

代わりに WebRTC の性質を使う：

```
準備フェーズ  pc.addTransceiver('audio', { direction: 'sendrecv' })
              → トラック無しで ICE / DTLS を完了させる（無音を送っている状態）

録音開始      sender.replaceTrack(micTrack)
              → 再ネゴシエーション不要・即座に音が通る
```

`replaceTrack` は SDP の再交渉を伴わない。これにより：

- **`recorder.ts` を変更しない**（既存の制約を維持）
- `getUserMedia` は録音開始時の1回だけ＝**マイクは本当に録音中しか動かない**（`track.enabled = false` より正直）
- ICE は録音開始前に完了している＝**最初の掛け合いを取りこぼさない**

マイクの受け渡しは `startUploadRecorder()` に**任意のコールバックを1つ足す**だけにする。配線は既に全ての配線が集まっている `useGameSocket` に置く。

マイク拒否の端末はコールバックが呼ばれず、無音を送り続ける＝**他の人には「その人の声だけ聞こえない」**という正しい劣化になる。

### 5.2 新モジュール `client/src/liveAudio.ts`

```ts
export type PeerState = 'connecting' | 'connected' | 'failed'

/** 準備フェーズで呼ぶ。全ピアと接続を張るが、まだ音は出さない。冪等。 */
export function startLiveAudio(params: {
  selfDeviceId: string
  peerDeviceIds: string[]
  onPeerState: (deviceId: string, state: PeerState) => void
}): void

/** 録音開始で呼ぶ。マイクを差し込み、リモート再生の muted を外す。 */
export function enableLiveAudio(micStream: MediaStream): void

/** 録音終了・中断・退出・解散で呼ぶ。全接続を閉じ、<audio> を撤去する。冪等。 */
export function stopLiveAudio(): void
```

**offer の主導権**は `deviceId` の辞書順で決める（小さいほうが offer を出す）。双方が同時に offer を出す glare を、追加のやり取り無しで防げる。この判定は純粋関数として切り出しテストする。

`RTCConfiguration`（STUN サーバーの一覧）は**このモジュールの定数1箇所**に閉じ込める。将来 TURN を足すときに設定を追加するだけで済むようにするため。

### 5.3 音の配線

`ontrack` でリモートストリームが届いたら**2箇所に繋ぐ**：

```
BGM/SE ──────────→ master ──→ ctx.destination（スピーカー）
                          └──→ mixDest
マイク ───────────────────────→ mixDest のみ
リモート音声 ─→ <audio muted autoplay playsinline>（スピーカー・AECの参照信号）
            └─→ audioBus.connectRemote() → mixDest のみ
```

`audioBus` に既存の `connectMic` / `disconnectMic` と**対になる形**で `connectRemote(deviceId, stream)` / `disconnectRemote(deviceId)` を足す。mixDest にだけ繋ぎ、スピーカー側には繋がない（二重に鳴るため）。

**なぜ `<audio>` 要素で鳴らすのか（罠1）**: ブラウザのエコーキャンセラは「スピーカーに出た音」を参照して打ち消す。リモート音声を Web Audio 経由（`ctx.destination`）で鳴らすと、この参照信号から外れることがあり **AEC が効かなくなる**。`<audio>` 要素は AEC が想定している経路である。

**iOS の無音バグ（罠2）**: iOS Safari は、リモートストリームを `<audio>` 要素に付けないと `createMediaStreamSource` が無音になる。上の配線は必ず `<audio>` に付けるため、偶然ではなく必然的に回避できている。

**自動再生ポリシー（罠3）**: `<audio>` は `muted` なら再生を許される。準備フェーズでは `muted = true` で `play()` しておき、録音開始で `muted` を外すだけにする。ユーザー操作（「準備完了」ボタン）を経たあとなので、この解除は通る。

### 5.4 ライフサイクル

| 契機 | 動作 |
|---|---|
| `script_ready`（配役画面）で `ctx.liveAudio === true` | まだ何もしない |
| 準備画面の「準備完了」を押したとき | `startLiveAudio()`。ユーザー操作起点なので `<audio>` の `play()` と `AudioContext` の resume が両方通る |
| `recording_started` | `startUploadRecorder()` がマイクを取得 → コールバック → `enableLiveAudio(stream)` |
| `recording_stopped` / `game_aborted` / `room_dissolved` / `leave_room` / `disconnect` | `stopLiveAudio()` |
| ゲーム中に再接続した端末 | **その回のライブ音声には戻らない。** 録音も記録されない回（`rejoinedNoRecord`）なので扱いが一貫する |

## 6. UI

### 6.1 ロビーのトグル

ジャンル選択のすぐ下に置き、**既存のジャンルUIと同じ形**にする（ホストは操作可、ゲストは表示のみで「ホストが選択」バッジ）。新しい操作の作法を発明しない。

```
┌ ジャンルを選ぶ ────────────┐
│ 💕恋愛  👻ホラー  😂コメディ …│
└───────────────────────────┘
┌ 声の配信 ──────────────────┐
│  [ ON ]   OFF                │
│  録音中、他の端末の声が        │
│  聞こえます                   │
└───────────────────────────┘
```

無効化の条件は2つあり、**理由を出し分ける**：

- 端末が1台だけ → 「他の端末が参加すると使えます」
- 端末が `MAX_LIVE_AUDIO_DEVICES` を超えている → 「◯台までです（いまは△台）」

### 6.2 録音画面の接続状態

**繋がらない人がいることが前提の機能**なので、それを隠さない。録音画面に控えめに出す：

```
🔊 声の配信中  ミチ ✓  タロウ ✓  ジロウ ✕
```

`✕` の人には「**声が聞こえないだけで、その人の録音と採点は正常**」という注記を添える。ここを黙っていると、ユーザーは録音そのものが失敗したと誤解する。

### 6.3 失敗時に再試行しない

接続に失敗したピアへの**再試行は実装しない**。リトライは状態機械（いま何回目か・いつ諦めるか・相手も同時にリトライしていないか）を増やし、**自動テストで守れない領域が広がる**。ベストエフォートと決めた以上そこを徹底する。

実際に失敗率が高ければ、次の手は順に **ICE restart 1回 → TURN の導入**である。設計としてどちらも塞がない（`RTCConfiguration` を1箇所に閉じ込めてあるので、TURN は設定を足すだけで入る）。

## 7. 既存機能との相互作用

| 相手 | 影響 | 扱い |
|---|---|---|
| **採点** | アップロードは `getUserMedia` の生ストリームのままで、**Web Audio を経由しないため構造的にリモート音声は混ざらない**。混ざるのはスピーカーからの回り込みのうち AEC が取り切れなかった分だけ | プロンプトは**変更しない**（既存の「他人の声が紛れ込む前提」の指示で足りる）。実機確認項目にする（9節） |
| **C（合体作品）** | 鑑賞用トラックが「自分の声＋BGM/SE＋**他全員の声**」になり、そのまま完成作品になる | 結果画面の見出し条件を「端末が1人 **かつ** 配信OFF」のときだけ「自分の演技を聞く」に。配信ONなら1人端末でも「みんなの熱演を聞く」が正しい |
| **ローカル複数プレイヤー** | mesh は端末単位なので、1台に3人乗っていればその端末は3人ぶんの声が入った1本を送る | 追加の考慮不要 |
| **1人プレイ** | ピアがいない | トグルを無効化（6.1節） |
| **ホスト切断＝即解散** | ライブ音声も一緒に落ちる | 既存挙動のまま。**繰り越しの B6 の重みがまた増える** |
| **AI枠・課金** | 一切関係しない | **1ゲームあたりの追加コストはゼロ** |

## 8. 帯域とバッテリー

5台の mesh で各端末が上り4本・下り4本。Opus は 24〜32kbps 程度なので合計 **128〜256kbps** 前後。モバイル回線で通る水準だが、**バッテリーは目に見えて食う**。録音は最長150秒なので実用上は問題にならないはずだが、実機で見るべき項目とする。

## 9. テスト方針

### 9.1 自動テストで守れるもの

サーバーのシグナリングは全部テストできる。既存の socket.io 統合テストの流儀（`startTestServer` ＋ `once` ＋ `expectNoEvent`）がそのまま使える。

| ファイル | 検証内容 |
|---|---|
| `server/tests/handlers.liveAudio.test.ts`（新規） | `set_live_audio` がホスト以外から無視される／`waiting` 以外で無視される／`live_audio_changed` が全員に届く／`RoomSnapshot` に載る |
| 同上 | `rtc_signal` が**別の部屋の端末には中継されない** |
| 同上 | `liveAudio` が OFF のとき中継されない／`waiting` や `evaluating` のとき中継されない／切断中の端末へは中継されない |
| 同上 | **なりすまし防止**：クライアントが `data` に偽の送信元を入れても、サーバーが付ける `fromDeviceId` が正しい送信者になる |
| 同上 | シグナルのレート制限が効く |
| 同上 | 端末数が上限を超えた状態で `start_game` すると `liveAudio` が false に落ちる |

クライアントは**純粋関数に切り出せるものだけ**テストする（React のテスト基盤が無いため）：

- **offer の主導権判定**（`deviceId` の辞書順）
- **接続先の算出**（`players` と自分の `deviceId` から他端末の一覧を出す）
- **トグルの無効化条件**（有効 / 1台 / 上限超過 の3状態）

### 9.2 自動テストで守れないもの

**この機能の中核は自動テストで守れない。** `RTCPeerConnection` は Node にも jsdom にも存在せず、このプロジェクトにはブラウザを自動操作する手段もない（Windows の権限制約で Playwright が使えない）。

守れないのは具体的に：**実際に音が聞こえるか／遅延の体感／エコーの発生／AEC の効き／iOS の自動再生／`replaceTrack` が本当に再ネゴ無しで通るか／`createMediaStreamSource` が iOS で無音にならないか**。

これは**このプロジェクトでこれまでで最もテストできない機能**である。ローカル複数プレイヤーは「画面3つが自動テスト無し」だったが、Dは**機能の心臓部そのものが検証不能**である。実機確認の比重を上げる。

### 9.3 実機確認（2台以上・別ネットワーク必須）

**同じ Wi-Fi の2台では意味がない。** NAT越えの検証にならないので、少なくとも1台はモバイル回線にすること。

1. 声が聞こえるか。遅延は掛け合いとして成立するか
2. **ハウリング／エコーが起きないか**（イヤホンなし・スピーカー再生で）
3. **帰属精度が落ちていないか** — ライブ配信ONで演じた回の採点コメントが、他人の演技を指していないか（**最大の懸念**）
4. **鑑賞用トラックに全員の声が入っているか** ＝ C が実際に手に入ったかの確認
5. 接続に失敗したときの表示が出るか（片方を機内モードにする等）
